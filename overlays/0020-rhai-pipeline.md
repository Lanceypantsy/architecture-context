## Fact

`rhai/pipeline` is the **package index management system** for all Red Hat AI
(RHAI) products. It does not compile wheels — compilation is fully delegated to
the `redhat/rhel-ai/wheels/builder` system, which provides global constraints,
security constraints, and variant-specific build requirements. Constraint files
in this repo must not conflict with the builder's constraints. This repo declares
which packages to build per collection × variant × architecture, and publishes
approved wheels to the customer-facing Pulp index.

This repo is part of the **fondue monorepo** (`redhat/rhel-ai/wheels/fondue`);
the pipeline lives at `rhai-pipeline/` within that monorepo.

Some products (notably RHAIIS) also maintain their own dedicated pipeline repos
(`rhaiis/pipeline`), though certain variants and collections are duplicated
across both repos.

- **Product name:** `rhoai`
- **Product version:** `3.6`
- **Pulp domain:** `public-rhai`
- **Public index base URL:** `https://packages.redhat.com/api/pypi/public-rhai/rhoai/`

Torch versions are pinned per variant via `constraints-rules.txt`. cpu, cuda13.0,
and cuda12.9 share torch 2.13.0; rocm7.14 pins torch 2.12.0; spyre pins torch
2.11.0. vLLM `+rhaiv` tags indicate the NeuralMagic enterprise fork; `.spyre`
indicates the IBM fork (`vllm[tensorizer]==0.25.1+rhaiv.1.spyre`). `cuda12.9-ubi9`
is excluded from the `rhaiis` collection because vLLM dropped CUDA 12 support.
ROCm 7.1 has been fully retired. A `tpu-ubi9` variant exists in the `rhaiis`
collection directory but Red Hat's public index does not yet serve TPU packages;
it is not in `publish_config.yml`.

Distribution URLs follow the dual-repo pattern (ADR 0199): test distributions
use a `-test` suffix; production distributions use `-prod`. The legacy unsuffixed
form (`rhoai/3.2/cpu-ubi9/simple/`) is preserved for older releases.

### Collections and Variant Coverage

The CI matrix is generated by `make regen` from `ci-job-definitions.yml` (monorepo
root) into `.generated/rhai-<collection>.yml` files. The `ci-job-definitions.yml`
is the authoritative source for collection names, variant lists, and optional
keys (`enable_test_jobs`, `enable_multi_version_bootstrap`, `max_release_age`).

Publishing to Pulp is controlled per **variant** in `publish_config.yml`, not
per collection. For default-routed collections, all wheels for a published variant
end up in the same public `public-rhai` Pulp index. For 3.6, the published
variants are: cpu-ubi9, cuda12.9-ubi9, cuda13.0-ubi9, rocm7.14-ubi9, and spyre-ubi9.

**Exception — `vllm-deps`:** This collection uses a collection-level `overrides:`
block in `ci-job-definitions.yml` to route to the private `rhai` Pulp domain
(`PRODUCT_NAME: "vllm-deps"`, `PRODUCT_VERSION: "torch2.11"`). Its wheels do
not appear in the public variant index. Deletion and promotion behavior for this
collection follows the same pipeline mechanics as other collections; the available
documentation does not establish any difference.

**Exception — `rhaiis` variant_overrides (`gaudi-ubi9`, `neuron-ubi9`, `tpu-ubi9`):**
Three variants in the `rhaiis` collection use `variant_overrides` in
`ci-job-definitions.yml` to route to the **private** `rhai` Pulp domain
(`https://private.console.redhat.com`), separate from the public `public-rhai`
domain used by the same collection's other variants (AIPCC-28553). These variants
carry vendor wheels (Habanalabs/Gaudi, AWS Neuron SDK, Google Torch/XLA) that
cannot be publicly redistributed. The routing precedence is:
`_default → overrides.<collection> → variant_overrides.<collection>.<variant>`.
The three variant-overridden variants publish to the private index even though
they belong to the `rhaiis` collection, which has no collection-level routing
override.

`ogx` has multi-version bootstrap enabled with a 30-day maximum release age.
`torch-day0` has multi-version bootstrap enabled with a 60-day maximum release age.
Both allow builds against multiple simultaneous product versions.

**Explicit exclusions from the build matrix (`omit_jobs` in `ci-job-definitions.yml`):**
- `[docling, cpu-ubi9, s390x]` — PDFium does not support s390x
- `[sdg-hub, cpu-ubi9, s390x]` — sdg-hub depends on Docling
- `[ogx, cpu-ubi9, s390x]` — no s390x index for this collection

**Variant linter** (`bin/variant-linter.py`) reads `ci-job-definitions.yml` on
every MR and blocks any variant not matching an approved pattern (cuda, rocm,
cpu, spyre, tpu). New accelerator types require approval from Doug Hellmann
before the pattern is added.

**Pulp routing exceptions:** Two mechanisms override the default `public-rhai`
domain. (1) **Collection-level** (`overrides.<collection>`): `vllm-deps/torch-2.11`
→ private `rhai` domain (`PRODUCT_NAME: "vllm-deps"`, `PRODUCT_VERSION: "torch2.11"`;
AIPCC-19939, ADR0211). (2) **Variant-level** (`variant_overrides.<collection>.<variant>`):
`rhaiis/gaudi-ubi9`, `rhaiis/neuron-ubi9`, `rhaiis/tpu-ubi9` → private `rhai`
domain (AIPCC-28553). Variant-level overrides apply after collection-level overrides
(`_default → overrides.<collection> → variant_overrides.<collection>.<variant>`).
All other collections and variants use the default public `public-rhai` domain.
See the Collections table entries for per-exception rationale.

### Onboarding Pipeline

New dependency requests land in `collections/onboarding/{variant}/` first.
Test builds are enabled (`ENABLE_TEST_JOBS: true`), giving teams CI feedback
before production. A weekly scheduled GitLab job (`move-onboarded-packages`,
triggered by `SCHEDULE_TYPE=move-onboarded`) runs
`./bin/move-onboarded-packages.sh`, which calls the `migrate-onboarding` CLI
tool, moves graduated packages to
`collections/rhai/*/requirements/onboarded.txt`, and creates a bot MR. All new
top-level dependencies must go through onboarding before appearing in the `rhai`
collection.

### Pipeline Flow

**Stages:** checks → lint → bootstrap → build → release → package-deletion →
publish → pre-notify → notify

**Trigger types:**
- Push to branch: standard CI (cancels concurrent interruptible jobs, except on
  main)
- Nightly schedule (`SCHEDULE_TYPE=nightly`): main branch builds only
- Weekly `move-onboarded` schedule: runs `move-onboarded-packages.sh`
- CVE scan schedule: runs `bin/cve_scanner.py`
- AutoQA trigger: fires HTTP POST to AutoQA when `publish_config.yml` changes

**Key checks-stage gates:**
- `variant-linter` — validates variant names in `ci-job-definitions.yml` on every MR
- `verify-publish-config` — on `publish_config.yml` changes, queries Pulp API
  to compare old vs new versions; saves `publish-delta/index-delta.md` as 90-day
  artifact
- `validate-package-deletion-manifests` — validates deletion YAML on MR; on
  merge, executes actual deletion

### Pulp Publishing Mechanics

**Two-stage workflow (dual-repo architecture, ADR 0199):**

1. **Upload** (`uv run pulp upload`): Discovers wheel/sdist artifacts, filters
   packages listed in deletion manifests, uploads via mTLS to Pulp, creates or
   updates a `-test` distribution (auto-increment pointer for QE). Labels each
   artifact: accelerator, rhel_version, variant, product_version, ci_commit_sha.
   Test and production are now separate Pulp repositories.

2. **Publish** (`uv run pulp publish`): Reads per-variant
   `WHEEL_REPO_VERSION`/`SDIST_REPO_VERSION` HREFs from `publish_config.yml`;
   updates the production distribution to point to the specified, tested, immutable
   repository version. The `update-publish-config-from-test` CI job automates
   querying the latest test HREFs and creating an MR to update `publish_config.yml`.
   Customers access packages only after this stage completes.

**Repository naming (ADR 065 + ADR 0199):**
- Wheels repo: `rhoai-{version}-{variant}` → path `rhoai/{version}/{variant}-prod/simple/`
- SDists repo: `rhoai-{version}-{variant}-sdists`
- Test distributions: `-test` suffix (`{base_path}-test/simple/`)

**Authentication:** All Pulp operations use mTLS (`PULP_CERT_BASE64` /
`PULP_KEY_BASE64` CI/CD variables). Builder cache deletion requires `BOT_PAT`.

> Note: `bin/upload_to_pulp.sh` and related shell scripts are deprecated wrappers.
> Use `uv run pulp upload/publish` directly.

### Package Deletion System

YAML manifests in `package-deletions/{release}.yaml` declare packages to remove.
Deletion is enforced at upload time (packages matching deletion patterns are
skipped before upload, preventing re-introduction even if builds re-run). MR
validation runs a dry-run; on merge the job executes actual Pulp deletion and
purges the GitLab PyPI cache. For dual-repo releases, deletion targets both
`-test` and `-prod` repositories. The system is idempotent.

### Version Branching

`uv run pulp copy` copies existing Pulp repositories to new repository names
when creating a new product version (e.g., EA2 → GA). The command computes the
variant intersection from `supported_versions.yml` — only variants present in
both source and destination get copied. This is a fast promotion path that does
not require re-running builds.

## Impact on Strategies

- This is the authoritative publish gate for all RHAI Python packages. No package
  reaches the customer-facing Pulp index without going through this pipeline.
- Adding a new collection or variant requires: (1) adding an entry to the
  `collections:` section in `ci-job-definitions.yml` at the monorepo root,
  (2) creating `rhai-pipeline/collections/{name}/{variant}/` directory structure
  with `requirements.txt`/`constraints.txt`, (3) running `make regen` to generate
  `.generated/rhai-{name}.yml`, (4) merging all three changesets together. The
  `variant-linter` CI job blocks any unrecognized accelerator type.
- All release branch jobs use `ENABLE_REPEATABLE_BUILD_MODE`. On a release branch,
  adding or updating a package requires explicit version pinning — the locked
  dependency graph will not re-resolve.
- Two CUDA versions (12.9 and 13.0) are maintained simultaneously. Adding a third
  is structurally straightforward but doubles builder resource consumption for
  that variant. `cuda12.9-ubi9` does not receive vLLM packages (vLLM dropped CUDA
  12 support upstream).
- ROCm 7.1 has been fully retired. Only ROCm 7.14 is built and published. ROCm
  7.14 now pins torch 2.12.0 (one minor below the CUDA variants' 2.13.0 — this
  is an intentional per-variant split, not an oversight). RFEs referencing ROCm
  should specify 7.14 and note the different torch pin.
- Spyre carries IBM-proprietary packages: `vllm[tensorizer]==0.25.1+rhaiv.1.spyre`
  (IBM fork, `.spyre` suffix distinguishes it from the NeuralMagic fork),
  `sendnn-inference==2.5.2` (IBM inference runtime, compiled from source),
  `torch-sendnn==1.3.0` (pre-built, x86_64 and ppc64le, private Pulp index),
  `torch-nnpa==1.5.0` (pre-built, s390x only, private Pulp index),
  `ibm-fms==1.13.0` (Foundation Model Stack, built from source; both pinned and
  unpinned `ibm-fms` are listed per AIPCC-27741), `spyremetrics==0.5.0` (ppc64le
  only, AIPCC-28704), and `ibm-aiu-smi==1.3.0` (ppc64le only, AIPCC-28706).
  Torch 2.11.0 is shared with other variants via `constraints-rules.txt`.
  `aiu-monitor`/`ibm-aiu-monitor` are blocked from all wheel collections and
  live in the base image instead. RFEs touching Spyre must account for this
  separate, IBM-controlled stack.
- The public index URL structure (`rhoai/{version}/{variant}-prod/simple/`) is
  treated as a stable contract for air-gapped mirroring (`wget`-based). Breaking
  this structure requires coordinating all downstream consumers.
- Package deletion is idempotent and enforced at upload time. RFEs proposing
  package removal must go through the deletion manifest process; simply removing
  a package from `requirements.txt` does not remove it from Pulp.
- New packages must go through the `onboarding` collection first. The weekly
  graduation automation handles promotion to `rhai`, but it runs weekly, not on
  demand.

### ROCm Work Breakdown Patterns

When a strategy involves a ROCm variant update in the pipeline (e.g., new ROCm
version or ROCm package changes), the pipeline-side work decomposes into these
epics:

- **Update ROCm variant constraints** — torch pin, vllm pin, and ROCm-specific
  package versions in `constraints.txt` and `constraints-rules.txt` for the
  `rocm{version}-ubi9` variant.
- **Add or update ROCm-specific packages in collections** — `amd-quark`,
  `amd-aiter`, `tensorflow-rocm`, `flash-attn`, and any new AMD ecosystem packages
  in `collections/rhaiis/rocm{version}-ubi9/requirements.txt`.
- **Validate build and publish for the ROCm variant** — CI pipeline green, wheels
  uploaded to Pulp, customer-facing index updated, `publish_config.yml` updated
  to point to the new Pulp repository version.

Strategies referencing ROCm pipeline updates should structure their Technical
Approach around these epics rather than describing the work as prose.

## Context

This overlay was created to capture the state of the RHAI wheel pipeline at the
3.6-EA1 release boundary and updated to reflect the current 3.6 (GA) state. The
pipeline repo is purely declarative — it contains no application code. Its
architecture (collection structure, variant matrix, Pulp publishing contract)
shapes what RHAI customers receive and constrains what RFEs can realistically
propose. This overlay allows the feasibility reviewer to evaluate whether a
proposed change is compatible with the existing index structure, build
infrastructure, and publishing workflow. Updated 2026-09-16 by running the `update-rhai-pipeline-overlay` skill against
the fondue monorepo at `../fondue/rhai-pipeline`. Corrected: `torch-day0` collection
variants (cpu-torch-day0-ubi9 and cuda13.0-ubi9 only; cpu-ubi9 removed); multi-version
bootstrap attribution (ogx/30-day and torch-day0/60-day; model-opt has no such setting);
omit_jobs list (actual exclusions: docling, sdg-hub, ogx on cpu-ubi9/s390x). Pulp routing
documents `vllm-deps` as collection-level exception and `rhaiis/gaudi-ubi9`,
`rhaiis/neuron-ubi9`, `rhaiis/tpu-ubi9` as variant-level exceptions per
`variant_overrides` in `ci-job-definitions.yml` (AIPCC-28553).
